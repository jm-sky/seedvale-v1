## Contact contract (written 2026-11-05, Q150 — slice A; code-verified, tests in `src/player/playerMeleeContact.test.ts`)

Status: contract text only; **no behaviour changed** (lunge frozen, no catalog numbers touched). Consumers (fauna-051) read this before editing shared interfaces.

1. **Reach semantics.** `MeleeConfig.range` is the centre-to-centre XZ distance between the attacker's position and the candidate's `(x, z)`; the arc is `dot(forward, dirToCandidate) >= arcDot` with `forward = (-sin yaw, -cos yaw)`. No height, shape, radius or raycast. One predicate (`resolveMeleeHits`) is the only authoritative final test; NPC approach gates (`dist <= melee.range`) use the same meaning. Size-aware reach (`MeleeHitCandidate.radius`, default 0) stays **not implemented** until §C evidence demands it.
2. **Timeline of one player attack.** Request frame: acquisition (`COMBAT_TARGET_RANGE` 7 m) -> `requestAttack` computes the bounded lunge -> `player.gapClose()` applies it **collision-resolved** -> `attackYaw` is locked from the *post-lunge* position to the target position at request (items-player-011). Hit edge (`hitReady`, >= `windUp` later): candidates are read at impact from the current frame (`GAZE_RANGE` 5 m, spatial-context filtered), attacker position is the current one, yaw is the locked one. Candidate position/liveness at impact is authoritative; the request-time target is not re-validated.
3. **Consequences (all accepted, tested).** (a) Reachable stationary target (`range < d <= range + MAX_LUNGE_DISTANCE - GAP_CLOSE_BUFFER`) is always hit if the lunge is not blocked. (b) Stationary target at `d > range + 2.9` up to 7 m: attack starts, lunge spends Stamina, hit whiffs — **accepted (author Q-C2 (a))**, not to be fixed via acquisition range/start gating/lunge. (c) A collision-shortened lunge that leaves the target beyond `range` yields no hit; nothing hits outside the final reach. (d) A target that leaves the locked arc or range during wind-up is not hit (no re-aim, no tracking — preserves "one attack, one yaw"). A moving-target fix (b) would need either live-yaw re-aim at impact (violates items-player-011) or a wider impact tolerance: **not implemented, author decision**.
4. **Hit cardinality (current, characterised — not changed).** `resolveMeleeHits` returns every live candidate in range + arc; `gameLoop` applies one damage event per returned id per swing (ids unique, dead animals skipped, wear once per hit). This holds for pierce/thrust weapons (knife, spear, ...) too, so a swing aimed at a wolf also damages an owned dog/livestock/rat standing in the cone (collateral). Whether pierce/thrust should become single-target (nearest/most-centred = the acquired target) and which weapons keep area swings is a per-weapon design choice the plan does not settle -> open author question (queue report), no code change yet.
5. **Not covered here.** Elevation mismatch, thin obstacles, cave entrances, distinct target sizes (verification item 4 shared half) wait for fauna-051 §A; Opus review gate precedes any shared-consumer edit or catalog retune.
