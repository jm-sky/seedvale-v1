## Reading and invariant contracts

Every donor ID appears once. “New” and a proposed runtime ID describe **future** integration, never current `ItemKind` registration. Only the reuse rows refer to existing V1 gameplay. Reserved IDs remain source-only. The separate **historical Stage 3** column records the unchanged reviewed mapping; Stage 4 outcomes do not retroactively reclassify it. Full [donor properties](./2026-10-27--equipment-property-matrix.md), own undefined keys, aliases, availability, tier, material, layer, grip, timing, typed damage/resist, durability and parry data remain lossless in the inert catalogue. This table is an integration view, not a replacement definition.

Profile owners and dependencies are defined in the [implementation proposal](./2026-10-27--equipment-stage-4-implementation-proposal.md#verified-source-ownership). Each new profile includes mass, size, base price, identity classification and truthful visual/UI presentation:

- **M:** `items/itemCatalog.ts` V1 melee `damage/range/arcDot/windUp/hitWindow/recovery/staminaCost`, defense, maintenance eligibility, held presentation, NPC family. Never convert V3 damage/reach/cooldown.
- **R:** same V1 owner, ranged damage/range/speed/draw/recovery/stamina/accuracy/crit and ordered ammo. No donor draw/reload conversion.
- **A:** same owner plus `armorItemInstances.ts` quality and `equipment.ts` slot/scalar reduction/restrictions; source `torso` targets V1 `body`. NPC/player mitigation uses shared rules, once. Shoulder/forearm integration requires **items-player-044**, including legacy saves; `leather_bracers` is registered once by that plan. No alias of `iron_vambraces` or `plate_vambraces` to `steel_bracers`.
- **Q:** count-backed V1 ammo definitions and shooter admission/order/consumption; `sling_stone` only for sling, `bolt_heavy/bolt_blunt` only for crossbow. Preserve original `stone` and `bolt` uses. Bonus values require V1 authorship; NPC/player differences must be reviewed in P3.
- **I:** inventory goods only; existing count serialization unless a concrete need justifies existing instance support. No armor, defensive, held or offhand config. Underlayers preserve `layer: under` and can later participate in real layered armor; current occupancy/mitigation must not encode a permanent ban on layers.

**U:** all 14 donor `unique` records receive A8 protection: seven source `legendary`, seven Unique/Exceptional despite source `tier: common`. This interpretation is separate from immutable donor fields. Exactly one live instance of each identity may exist per world; an identity can remain unissued. Every candidate reward/discovery/specialist offer shares **one world-level claim**, across all owners, sources and unloaded state. Source-level one-shot flags alone are insufficient. See [global issuance design and unresolved lifecycle questions](./2026-10-27--equipment-stage-4-implementation-proposal.md#global-identity-and-issuance-design). `iron_rimmed_shield` is quest-only Common in the donor; that flag does not make it Unique or Legendary. Its proposed keyed quest source must also resist repeated rewards.

**Source/NPC policy:** new rows name candidate source classes, not existing quests or enabled offers. P7 selects actual finite sources/prices and profession/settlement/wealth/resource fit through existing V1 stock, household, trade and NPC systems. Existing item-stock specializations are `general`, `weapons-tools`, `food-materials`, `imports-luxury`; armor/travel describe assortments, not new vendor roles (the existing `horses` specialization is outside this intake). NPCs use suitable owned active gear; inventory-only goods may be carried/traded but never supply defense. Masterwork is scarce, not globally unique. No blanket merchant/loot injection, new parallel economy, or fabricated production capability. Existing recipes may supply goods only after their actual input/output support is verified. Alternative U sources cannot each mint a specimen.

**Stage/dependency shorthand:** P0 fixes the bounded slice contract; P1 reviews exact compatibility-policy changes before a dependent profile is relied on. P2–P6 require P0/P1, separate slice authorization and D4 Performance-First exit. P5 additionally requires 044 and shared P4 armor contracts. Every new acquisition waits for P7; U acquisition also waits for P7a global issuance verification. P8 only tracks three deferred items. Stage order/details/tests/rollback belong to the proposal; these references confer no implementation permission.

**Persistence:** M/R/A instances use existing `createAcquiredInstance`, cloning, `toSaveItemInstance`, `Inventory.instancesFromJSON`, exact transfer/drop/restore and structural save validation. Q/I count keys round-trip without renames; I has no equipment/held references. A persists quality + equipped instance ID; 044 owns `arms→shoulders`. U adds durable issuance facts and owner cross-validation, not a parallel ownership store. Reserved records create no save rows. Coordinate real representation/semantic changes with the existing version/migration pipeline and D1; do not assume a save reset.
