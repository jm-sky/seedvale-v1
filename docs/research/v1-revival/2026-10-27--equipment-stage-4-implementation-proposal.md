## Global identity and issuance design

**Proposal, not implemented or author-approved lifecycle policy:** extend current app/world persistence composition with one small sparse **world issuance ledger**, keyed by canonical V1 item identity. Inventory continues to own the specimen; no new equipment inventory, centralized owner graph or renderer-managed identity. Existing per-owner maps and consumed source sets cannot alone enforce the global constraint: identical kinds can be minted under different instance IDs in multiple settlements or source systems.

The smallest proposed fact is `{ kind → instanceId, issuanceKey, lifecycleStatus }` for each claimed upper-tier identity, plus a durable tombstone if destroyed. The precise persisted shape is a P7a design deliverable. Do not store duplicate item payload/condition or another mutable owner field in the ledger. Existing inventory/container/drop/NPC records remain the authoritative payload and location. Current possession can be indexed transiently at restore/transfer verification, not polled every frame. An unissued identity has no live specimen; the invariant is **at most one live instance**, not mandatory creation on world startup.

- **Lifetime:** one ledger for the whole world, initialized before any source grant or deterministic stock reconstruction, retained through `WorldBundle` replacement and captured/restored through the same save/rebuild pipeline. Reset only with an explicit new world. It is not worldgen cache or per-settlement/per-chunk state. Loading an older snapshot restores that snapshot's whole world and ledger together; it must not merge an in-memory ledger from a different save. Cross-slot/world item transfer is not a supported acquisition route.
- **Issuance transaction:** source requests a claim for `kind` plus stable source key. Preflight destination capacity, source eligibility and ledger state, create the existing instance shape, then commit receipt + ledger + source/reward/stock marker in one synchronous all-or-nothing command. On failure restore all participants, including payment, without consuming the claim. Reentrant/double requests fail or return the already-owned specimen reference without adding it again. Do not create the specimen eagerly before the guard. All generic `createAcquiredInstance`/catalog-buy/grant/stock paths must be audited so none bypasses the claim. Source alternatives may compete for the same unissued identity; enabling several independent minting routes is forbidden.
- **Discovery before pickup:** a rendered available world pickup is already a live specimen. Claim and establish a durable instance payload/location when materializing it, not only when collecting it. Rebuild reprojects the same owned specimen and stable pickup ID. Current one-shot pickups with only `kind`/source consumption are insufficient for upper-tier gear unless they gain the narrow existing-instance payload bridge. Unmaterialized offers/rewards are promises, not independent copies. A merchant listing backed by real stock is live and must have claimed its specimen.
- **Transfers:** player/NPC/merchant/household/container/cargo/corpse/drop moves preserve exact instance ID and ledger claim. Held/equipment/primary references and meshes do not count as extra specimens. Use `transferInventoryInstance` and existing full snapshots; an ownership transfer never calls the acquisition factory. Persist unloaded owners as well as live ones. Reject duplicate ID in two owners and two IDs for one restricted kind; per-inventory duplicate suppression does not suffice.
- **Merchant sales:** a finite shop is not a global limiter across shops/worlds. Specialist issuance must acquire the global claim before stock insertion; its latch must not reseed a claimed kind. Selling an upper-tier item must move that same instance to a durable existing stock owner with exact ID, or the unsupported sale path stays unavailable. Some current catalog sale paths remove items and award coins without retaining a concrete destination; they cannot silently destroy a sale then reopen issuance. Select the existing explicit-owner trade path rather than build another merchant inventory.
- **Container/corpse/death:** existing full Inventory snapshots and placed-container saves are suitable seams. Count-only treasure/loss/reconstruction helpers are insufficient for singleton payloads; either extend the concrete existing owner path narrowly or keep that particular source disabled. NPC death moves the same personal specimen into corpse loot; corpse cleanup/destruction needs the lifecycle policy below. Player/NPC equipment never creates a second copy.
- **Save/load integrity:** ledger, source markers and owners are one save snapshot. Validate exact kind/ID cardinality and ledger linkage across all persisted domains **before** acquisition, including merchant stock, household items, personal/cargo/corpse inventory, placed/carried containers and drops/pickups. Duplicate or contradictory claims reject load/write with diagnostics; do not silently delete, clone, re-ID or fall back to counts. Missing owners are not evidence of destruction. A schema/migration/version change is required only according to actual representation/semantics and existing save conventions; coordinate D1 without choosing a version number here. A missing ledger in a pre-feature save can start empty only after proving that no restricted instances/sources exist; otherwise migrate from all durable owners with a duplicate-rejection rule, or explicitly refuse incompatibility.

**Required P7a tests:** two sources for the same kind, two specialist merchants, merchant versus quest/discovery, repeated/reentrant claim, full destination/payment failure and source rollback; exact player↔NPC↔merchant↔household↔container↔cargo↔drop ownership; equipment references; NPC death/corpse loot/cleanup; save before and after issuance, reload of sold-out merchant and partially claimed reward; unload/rebuild/reconstruction in different orders; uncollected pickup reload; duplicate physical ID across owners and two physical IDs for one kind; corrupted/missing ledger linkage; write rejection preserving the old save; new world and switching saved worlds. Tests include every enabled production issuer, not just a standalone ledger fake. Tests exercise ownership failures and source atomicity, not per-frame world scans.

### Lifecycle questions to settle before upper-tier source activation

A8 fixes cardinality but does not decide reappearance policy. These are explicit unresolved design questions; no default below is an additional author decision.

| Event | Fixed boundary | Question / implementation condition |
| --- | --- | --- |
| Destruction, broken gear or container/corpse cleanup | Cannot free a claim simply because the current live inventory no longer has it | Is confirmed destruction permanent, or can a later authored source reissue? Prefer retaining a non-reissuable tombstone until policy is chosen; no automatic reissue in the interim. Which existing lifecycle event authoritatively proves destruction? |
| Loss, inaccessible drop, unloaded owner or missing runtime mesh | Unloaded/inaccessible is still owned/live; keep the same identity | How can truly unrecoverable loss be established, and is recovery allowed? Absence from loaded owners must never trigger replacement. A missing persisted payload is an integrity error, not a new reward. |
| Reload / crash / failed source command | Whole-world restore must contain at most one specimen and no half-issued payment/reward | Define transaction boundaries and stable IDs, verify snapshot consistency. Crash rolls back to the saved snapshot; it must not combine that with later source markers. No new product decision required for atomicity. |
| Transfer / sale / death | Exact ID and claim survive normal ownership changes | Identify durable destinations and disposal semantics for every enabled path; unsupported destroying-sale/cleanup paths stay closed until designed. Transfer itself needs no author confirmation. |
| Reappearance after confirmed destruction/loss | Any permitted replacement must still satisfy one live specimen and no parallel source | Product policy may require author input if replacement is desired; A8 does not authorize unlimited or automatic respawn. Retaining the claim safely permits technical work without reopening A8. |

No broad global-ownership rewrite is required by this recommendation. It is a cross-source issuance/integrity extension to existing state owners. Independent review of the final P7a protocol and enabled source set is an acceptance condition before availability.
