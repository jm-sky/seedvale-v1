## 2. Baseline: measure the right problem before porting

Historical V1 [performance owner](https://github.com/jm-sky/seedvale-v1/blob/e693cbff7bc873e8cc2a7cdf6868138ea33839dd/docs/performance/README.md) and [2026-09-21 settlement-heavy benchmark](https://github.com/jm-sky/seedvale-v1/blob/e693cbff7bc873e8cc2a7cdf6868138ea33839dd/docs/performance/results/2026-09-21--030--benchmark-settlement-heavy.md) report High, 1920×945, seed 42, spring/rain: 22.2 average FPS, frame p95 65.6 ms, ~2,311 actual average renderer draw calls and 8.00M average triangles, with a separate scene census estimate. Render isolation measured 23.3 ms full versus 14.4 ms with NPC/fauna hidden and 19.1 ms with settlement content hidden. These are **exposed costs of removed content, not recoverable savings, additive GPU pass costs or acceptable output**. The NPC category measured ~4.7 ms/frame in that settlement; the stream scenario's cold river-tile stages previously recorded ~43–51 ms individual builds. All numbers predate current revival changes and need new-device reproduction.

V1 already implements:
- [terrain worker pool](https://github.com/jm-sky/seedvale-v1/blob/e693cbff7bc873e8cc2a7cdf6868138ea33839dd/src/terrain/chunkWorkerPool.ts), [worker mesh extraction and bounded 64 MiB data cache](https://github.com/jm-sky/seedvale-v1/blob/e693cbff7bc873e8cc2a7cdf6868138ea33839dd/src/terrain/chunkMeshCache.ts), nearest-first/budgeted [chunk finalization](https://github.com/jm-sky/seedvale-v1/blob/e693cbff7bc873e8cc2a7cdf6868138ea33839dd/src/terrain/chunkManager.ts);

- [shadow update policy](https://github.com/jm-sky/seedvale-v1/blob/e693cbff7bc873e8cc2a7cdf6868138ea33839dd/src/render/shadowBudget.ts), [GPU timer](https://github.com/jm-sky/seedvale-v1/blob/e693cbff7bc873e8cc2a7cdf6868138ea33839dd/src/perf/gpuTimer.ts), [scene and agent detail census](https://github.com/jm-sky/seedvale-v1/blob/e693cbff7bc873e8cc2a7cdf6868138ea33839dd/src/perf/sceneCensus.ts), [benchmark scenarios](https://github.com/jm-sky/seedvale-v1/blob/e693cbff7bc873e8cc2a7cdf6868138ea33839dd/src/perf/benchmarkScenarios.ts) and isolation probes.

## 4. Navigation is a gameplay improvement opportunity

Separate the **search implementation** from the **navigation contract**. V1's real movement is governed by existing steering, stuck recovery, surface/collision, doors/bridges/caves and agent intent. V3's explicit outcomes such as not-ready (data/budget), unreachable and capped can improve user-visible behavior: avoid incorrectly treating a not-yet-prepared area as impassable; avoid retry bursts; distinguish temporary missing data from a genuine blocked route. But a new result contract changes callers and cannot be dropped in without adapters.

Suggested research suite before any replacement:
1. Snapshot representative V1 start/goal and context cases: busy villages and narrow gateways, interiors/doors, bridges and fords, steep or rocky terrain, riverbanks, caves/mouth transitions, trees that can be felled, construction/terrain modifications, NPC following/merchant deliveries, predator pursuit and fleeing.
2. Compare **reachability, travel completion time, path length/cost, detours, stuck/rescue count and failed commitments**, not only A* microbench throughput. Include cold cache, concurrent requests, cancellation after target/obstacle change and retry fairness.
3. Preserve existing V1 query and movement authority; try a local heap/array optimization first if CPU/GC warrants it, then design an explicit readiness/failure adapter and sliced work only when evidence supports better correctness/reliability.
4. For offscreen NPC orders test detailed↔offscreen handoff, inventories/provisions/cargo, arrival idempotency and time-skip. **Reject** V3 generic Far goal cancellation/elapsed dropping as a V1 runtime default.

R2 [C1/C2 and §5–6](./2026-10-25--002--architecture-and-simulation.md) already documents full navigation compatibility, the V3 scheduler trap and the cache replay limitations. This research adds a route-*quality* acceptance requirement, not a parallel nav architecture.

### 10.4 Culling and bounds contract

**Recommended first trial:** use native per-mesh frustum culling with cached, conservative per-instance skinned bounds on one NPC family. This reuses the renderer's existing main/light tests and leaves root visibility, optional-node visibility, material visibility and simulation untouched. Three's shadow renderer first rejects invisible ancestors, then performs its own frustum test; main-frustum-only root false therefore loses shadows by construction. The installed V1 `node_modules/three/src/renderers/webgl/WebGLShadowMap.js::renderObject` confirms this ordering (package implementation inspected, no runtime patch proposed).

An animated conservative envelope must cover Idle/Walk/Run, work, carried cargo, ranged/melee/hurt, sleep-entry, death and rolled fallback; head/hair/skirts, juvenile/member scale, exceptional fauna size, packs and antlers. A root-point census cannot supply that envelope. Prepare after final assembly; world-space conversion must include parent transform and maximum scale. Retest installation/hydration and dynamic scale changes. Prefer measured clip envelopes or documented conservative bounds; computing all skinned vertices each frame can erase the benefit. Unknown/missing bounds mean draw, not disappear.

**Whole-actor sphere test remains a conditional later experiment**, justified only if native per-mesh rejection leaves measured scene traversal/submission overhead. Reuse one frame camera matrix and the existing agent lists; derive relevance once, no second agent registry/spatial grid, no persistent visibility authority. To suppress a complete visual safely, reject only when conservatively irrelevant to all required passes (main and relevant shadow receiver/caster volume; agents already excluded from mirror). Merely intersecting the light frustum can retain extra actors but is a safe conservative starting point. A main-only root toggle is rejected. If native culling wins enough, stop there.

Before any explicit visual visibility composition, identify lifecycle visibility separately and combine `lifecycleAllowed && renderRelevant` at one owner. Keep `mesh.visible` semantics for corpse loot/expiry, `hideLivingVisual` and material visibility; do not restore all descendants indiscriminately. NPC has a convenient child model root; fauna capsule is itself the spatial mesh, so the same wrapper recipe cannot be copied blindly. Such a composition adapter is local to existing presentation ownership, not a second global visibility system.

### 10.5 CPU cadence, return to view and gameplay hazards

Mixer advancement changes bones and crossfades, not authoritative NPC movement. Existing V1 `agentAnimationSet` has no gameplay `finished` listener; combat and one-shot/sleep timers live in agents. Nonetheless each callsite must be checked before throttling: intent can change while mixer is paused, old elapsed time must not be applied to a newly started attack, hurt, sleep or death clip.

For the first NPC cadence experiment, use **distance-only bounded ordinary-loop cadence**, with full rate near the player and for combat/hurt/sleep entry, conversation and any uncertain transition. Keep intent/important-state detection every tick, and reset/flush accumulated presentation time at semantic clip changes. Retain current death path unchanged. Bound playback delay, stagger stable IDs without new randomness, force current pose before first newly important/visible submission. Do not replay a long hidden interval through a newly selected action or execute catch-up simulation steps. Keep shadow-visible bones sufficiently current; a visible moving shadow also needs presentation even if actor is off camera.

Off-camera mixer skipping is a **separate, later** experiment requiring shared camera relevance from the culling owner and a tested re-entry contract. Re-entry must show current pose/held gear immediately, respect current sleeping/dead state and not replay stale attacks. Do not tie bark/audio delivery, pending conversation voice, needs, decision selection, ground/water, crowd separation, hit/range tests, household work, travel, drowning, corpse expiry or harvest to that predicate. Label/overlay work can be measured separately; CSS2D visibility is not simulation relevance.

### 12.8 Acceptance, risks and evidence limits

**Matched comparison:** same V1 save/new-world fixture, authored route/camera, lighting/weather/clock, ground shader, quality/fog, resident NPC/fauna/settlement population and functional state. Separate (a) backend change at fixed placement/shape where possible, (b) visual density/shape/profile tuning. The production candidate can change decorative sampling, but report visible cover and accepted populations explicitly so a thinner meadow is not mislabeled as architectural savings. Capture both per-renderer data and total frame behavior; compare alternating warmed arms (e.g. three pairs), record variance/thermal/power conditions, and separate shader compile/cold allocations.

Minimum scene matrix: close olive meadow in motion; dense wilderness/forest edge; maintained settlement and yard; road→bridge/ford→river/lake bank; slope/edited ground; cave mouth and interior→exterior; long out-and-back travel, teleport and bundle rebuild. Repeat dry/rain/storm, low sun/night and snow override steps plus a separate running snow/melt/time-skip/save/load sequence. Profiles must blend without chunk/tile borders, blades must remain planted, and flowers must read as loose clusters without opaque squares, shimmer, upright rigid heads or disappearing bands. Inspect low/high existing quality presets; deferred device paths still compile.

**Evidence to record:** whole-frame CPU/GPU p50/p95/p99 and hitch count/max; generation, pool-write and upload preparation time; actual main/shadow/mirror/post submissions and submitted/accepted instances/triangles; first/full versus changed-block upload bytes/ranges; pending jobs, cold ring fill latency, pool exhaustion and dropped/overflow flowers; CPU typed-array/cache high-water and renderer geometries/textures/program trends across repeated travel/rebuild/dispose. Geometry/texture counts are leak indicators, not byte-accurate VRAM. Unsupported/disjoint GPU timers remain unavailable. Existing V1 `grassFinalizationDiag`, scene census, GPU timer and stream/settlement scenarios are starting points; extend only the missing attribution.

**Keep candidate only when** source-contract/regression checks pass, one-backend and disposal invariants hold, V1 world/save/resource behavior is unchanged, author accepts cover/palette/flowers/transitions, and matched results show a decisive repeatable net improvement beyond observed run variance without worse travel tails or unbounded memory. Agree numeric thresholds from C0 before C6; this research supplies no invented universal percentage. A grass-only GPU win that loses on total frame p95/cold fill is insufficient. If benefit is marginal, unknown or obtained only through unacceptable density loss, revert to legacy default and retain research evidence. Do not force default activation to complete a migration.

Highest risks: wrong rendered-surface sampling near edits/cutouts; stale source bytes after world mutation; copying short donor radii that expose bare ground under V1 fog; main-thread generation displacing an existing worker advantage; Lambert/day-night palette differences; dither/billboard overdraw and aliasing; broadleaf/flower suppression affecting unrelated vegetation; ring meshes losing V1 pass exclusions; duplicate resources/late callbacks across rebuild; bounded slots silently truncating rich V1 patches. These risks require prototype evidence, not simulation simplification or terrain replacement.

**This session's verdict:** research complete; no runtime/build/test/browser/GPU acceptance claimed, no FPS gain established. Next eligible action is implementation-contract review and authorization for C0/C1, not full renderer activation. The three-track checklist records research delivery separately from those open gates.
