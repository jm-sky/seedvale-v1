## 2. Baseline: measure the right problem before porting

Historical V1 [performance owner](https://github.com/jm-sky/seedvale-v1/blob/e693cbff7bc873e8cc2a7cdf6868138ea33839dd/docs/performance/README.md) and [2026-09-21 settlement-heavy benchmark](https://github.com/jm-sky/seedvale-v1/blob/e693cbff7bc873e8cc2a7cdf6868138ea33839dd/docs/performance/results/2026-09-21--030--benchmark-settlement-heavy.md) report High, 1920×945, seed 42, spring/rain: 22.2 average FPS, frame p95 65.6 ms, ~2,311 actual average renderer draw calls and 8.00M average triangles, with a separate scene census estimate. Render isolation measured 23.3 ms full versus 14.4 ms with NPC/fauna hidden and 19.1 ms with settlement content hidden. These are **exposed costs of removed content, not recoverable savings, additive GPU pass costs or acceptable output**. The NPC category measured ~4.7 ms/frame in that settlement; the stream scenario's cold river-tile stages previously recorded ~43–51 ms individual builds. All numbers predate current revival changes and need new-device reproduction.

V1 already implements:
- [terrain worker pool](https://github.com/jm-sky/seedvale-v1/blob/e693cbff7bc873e8cc2a7cdf6868138ea33839dd/src/terrain/chunkWorkerPool.ts), [worker mesh extraction and bounded 64 MiB data cache](https://github.com/jm-sky/seedvale-v1/blob/e693cbff7bc873e8cc2a7cdf6868138ea33839dd/src/terrain/chunkMeshCache.ts), nearest-first/budgeted [chunk finalization](https://github.com/jm-sky/seedvale-v1/blob/e693cbff7bc873e8cc2a7cdf6868138ea33839dd/src/terrain/chunkManager.ts);
- [3×3 regional vegetation instancing](https://github.com/jm-sky/seedvale-v1/blob/e693cbff7bc873e8cc2a7cdf6868138ea33839dd/src/terrain/vegetationRegionBatcher.ts), [grass geometry/density LOD](https://github.com/jm-sky/seedvale-v1/blob/e693cbff7bc873e8cc2a7cdf6868138ea33839dd/src/terrain/distanceLod.ts), fauna cadence and proximity indexing;
- [shadow update policy](https://github.com/jm-sky/seedvale-v1/blob/e693cbff7bc873e8cc2a7cdf6868138ea33839dd/src/render/shadowBudget.ts), [GPU timer](https://github.com/jm-sky/seedvale-v1/blob/e693cbff7bc873e8cc2a7cdf6868138ea33839dd/src/perf/gpuTimer.ts), [scene and agent detail census](https://github.com/jm-sky/seedvale-v1/blob/e693cbff7bc873e8cc2a7cdf6868138ea33839dd/src/perf/sceneCensus.ts), [benchmark scenarios](https://github.com/jm-sky/seedvale-v1/blob/e693cbff7bc873e8cc2a7cdf6868138ea33839dd/src/perf/benchmarkScenarios.ts) and isolation probes.

## 4. Navigation is a gameplay improvement opportunity

Separate the **search implementation** from the **navigation contract**. V1's real movement is governed by existing steering, stuck recovery, surface/collision, doors/bridges/caves and agent intent. V3's explicit outcomes such as not-ready (data/budget), unreachable and capped can improve user-visible behavior: avoid incorrectly treating a not-yet-prepared area as impassable; avoid retry bursts; distinguish temporary missing data from a genuine blocked route. But a new result contract changes callers and cannot be dropped in without adapters.

Suggested research suite before any replacement:
1. Snapshot representative V1 start/goal and context cases: busy villages and narrow gateways, interiors/doors, bridges and fords, steep or rocky terrain, riverbanks, caves/mouth transitions, trees that can be felled, construction/terrain modifications, NPC following/merchant deliveries, predator pursuit and fleeing.
2. Compare **reachability, travel completion time, path length/cost, detours, stuck/rescue count and failed commitments**, not only A* microbench throughput. Include cold cache, concurrent requests, cancellation after target/obstacle change and retry fairness.
3. Preserve existing V1 query and movement authority; try a local heap/array optimization first if CPU/GC warrants it, then design an explicit readiness/failure adapter and sliced work only when evidence supports better correctness/reliability.
4. For offscreen NPC orders test detailed↔offscreen handoff, inventories/provisions/cargo, arrival idempotency and time-skip. **Reject** V3 generic Far goal cancellation/elapsed dropping as a V1 runtime default.

R2 [C1/C2 and §5–6](./2026-10-25--002--architecture-and-simulation.md) already documents full navigation compatibility, the V3 scheduler trap and the cache replay limitations. This research adds a route-*quality* acceptance requirement, not a parallel nav architecture.

## 7. Preservation/integration risks and exclusions

- Authoritative V1 gameplay, simulation, timing and persistence stay V1-owned. Culling/LOD may affect **presentation only**. Visual root currently also supplies some pose/proximity state in V1; do not blindly hide/unload object instances and then assume game collision/interaction still works.
- Render batching must respect mutation/ownership boundaries (wood levels, storage/food, chopped trees, roads, caves, houses/doors and terrain edits); lifecycle cleanup and stale async responses must be checked.
- V3 tree impostors are not universally better at short V1 fog ranges. Large alpha cards can exchange triangles for overdraw and shadow differences; LOD changes can create visible density/popping regressions.
- V3 fern far tier intentionally drops half its records. **Do not transfer that population choice** without author approval; geometric savings with V1 density intact are the initial hypothesis.
- V3 piles are static authored overlay tier, while V2 piles are live-read and V1 already has deeper physical economy. Porting the V3 state behavior would make the V1 stacks dishonest.
- Old V1 shader prewarm experiments regressed; regional vegetation batching and worker/cache migration already shipped. Avoid another generic prewarm pass, a global vegetation mega-batch or a duplicate worker manager.
- No implementation files, runtime flags, asset bytes or benchmarks were modified as part of this recon.

### Port boundary and difficulty

A complete *grass presentation* replacement is **medium–high integration complexity**, not an asset drop-in: V3's [tilePlacement](https://github.com/jm-sky/seedvale/blob/199f98e215418999fc589891163afd321df7803f/src/game/render/grass/tilePlacement.ts) samples a terrain-query interface and interpolation aligned to its 2 m near mesh; V1's [chunkManager](https://github.com/jm-sky/seedvale-v1/blob/e693cbff7bc873e8cc2a7cdf6868138ea33839dd/src/terrain/chunkManager.ts) streams 64 m chunks with worker-produced terrain/grass, independent biome/road/river/cutout rules, and existing weather/vegetation ownership. V3 [coverField](https://github.com/jm-sky/seedvale/blob/199f98e215418999fc589891163afd321df7803f/src/game/render/coverField.ts) bakes a camera-centred mask used by both flowers/grass and terrain; importing it wholesale additionally couples ground shader composition and canopy updates to V1 lifecycle. V1 [terrain material](https://github.com/jm-sky/seedvale-v1/blob/e693cbff7bc873e8cc2a7cdf6868138ea33839dd/src/terrain/buildChunkGeometry.ts) already composes dirt textures, procedural noise, wetness, scorch and threshold snow through `onBeforeCompile`. Replacing that wholesale is a **separate higher-risk shader migration**.

**Proposed bounded sequence for a later approved plan:** (1) capture V1 baseline plus paired visual references; (2) verify donor geometry, band counts and V3 device benchmarks with equivalent quality settings; (3) design one V1 terrain/cover eligibility adapter that reuses authoritative V1 data, including worker/camera/streaming and cave exclusion, without duplicating simulation state; (4) implement reversible V3 grass/flower visual cutover behind a dev flag while ensuring only one runtime renderer is active; (5) run tests and device A/B through motion, streaming, biomes, seasons, snow and rebuild/dispose; (6) **keep the V3 renderer only if the advantage and look hold**, then separately decide whether V3 cover textures/noise/litter provide a worthwhile terrain-material upgrade. Preserve V1 navigation/worldgen regardless.

**Evidence gate:** Compare actual rendered density/silhouette and CPU/GPU p50/p95/p99, draw calls by pass, uploaded buffer ranges/allocations, cold tile/clipmap fill hitches and memory in matching V1 scenes. V3's published low millisecond grass deltas and bounded band triangle counts describe **V3 workloads**, not a directly demonstrated V1 improvement. Likewise, V1's 120,000 grass *placement candidates per chunk* cannot be compared numerically to V3's 192 *tile slots* without acceptance and culling measurements.

**Execution guidance:** A strong single model with direct repository access and reliable test/browser tools can research, plan and implement this migration in scoped stages; using Opus plus Sonnet is **not a technical prerequisite**. For a whole renderer/shader integration, an independent design or code review is a valuable risk reducer. Prefer one accountable implementer (GPT Sol or Sonnet/Cursor) with independent focused review (Opus or another capable reviewer) at the architectural boundary and again before removing V1's fallback. No parallel competing implementations; no work order is issued by this research addendum.
