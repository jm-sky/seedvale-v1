## 1. Scope

Reviewed only code correctness, architecture, lifecycle and performance for the existing audio runtime.

Traced:

```text
asset/load request
→ THREE.AudioLoader / LoadingManager / decode
→ module buffer cache
→ THREE.Audio / listener + mixer bus
→ playback trigger
→ distance/environment/cave state
→ fade/stop
→ app teardown / world rebuild
```

Covered ambient loops/events, weather/thunder, fire, NPC voice/barks/reactions, fauna vocalization, action/combat sounds, cave transitions, listener ownership and app/rebuild lifecycle.

Missing sound assets, music and subjective sound quality are intentionally not findings.

## 2. Entry points and state owners

### Shared runtime

- `src/audio/createWorldAudio.ts` owns the one app-level `AudioListener`, ambient/SFX `GainNode` buses, loop handles and one-shot playback API.
- `src/app/createApp.ts` creates `WorldAudio` after the render stack/camera, wires UI/NPC consumers, creates ambient/fire/weather audio, and tears those consumers down before `worldAudio.dispose()`.
- `WorldAudio` is app/session-owned, not a `WorldBundle` field. In-session bundle rebuilds therefore reuse one listener/mixer instead of duplicating it.
- `src/app/gameLoop.ts` feeds current weather, cave occupancy, environment and fire state into the app-owned audio projections and calls `worldAudio.update(dt)`.

### Asset/decode ownership

`src/audio/createWorldAudio.ts` has module-level:

```ts
const audioLoader = new AudioLoader()
const bufferCache = new Map<string, Promise<AudioBuffer>>()
```

`loadBuffer(url)` de-duplicates both in-flight and successful loads by URL.

The project currently depends on `three ^0.185.1`. Three r185 `Loader` defaults an omitted manager to `DefaultLoadingManager`; r185 `AudioLoader` starts an additional manager item named `url + '#decode'` before `decodeAudioData()` and ends it after decode.

Repository search found no Seedvale subscription to `DefaultLoadingManager.onLoad/onProgress/onError` and the startup loading screen is app-owned rather than manager-driven. Therefore the shared manager / `#decode` behaviour is verified, but is not itself a current Seedvale defect.

### Spatial/environment owners

- `playAt()` / `playAtCancelable()` read listener world position once and convert source distance to initial gain.
- They create ordinary `THREE.Audio`, not `THREE.PositionalAudio`; no source is attached to the emitting `Object3D`.
- `WorldSoundPosition.y` is optional. Missing Y is replaced with listener Y, making that trigger XZ-only.
- `createAmbientAudio.ts` uses the player `Caves.queryInterior(..., 'player')` state supplied by `gameLoop.ts`; surface beds/events are multiplied by the cave surface mix.
- `weatherSounds.ts` uses the same cave flag for rain/storm ambience.
- NPC/fauna callers generally pass live mesh positions (including Y) at trigger time.
- Several player/world action call-sites pass only `{ x, z }`.

## 3. Flows traced

### Ambient

`createApp → createAmbientAudio → WorldAudio.createLoop → loadBuffer → AudioLoader/decode → Audio → ambient bus`

Continuous forest/night/coast/wind/meadow/birds/frogs/cave beds have one handle each per `AmbientAudio` instance. Lazy handles are retained and faded rather than recreated. Cave entry immediately forces a resample and crossfades surface/cave targets. Ambient owl events are frame-driven, not timer-driven, and their `forestWeight` is multiplied by `mix.surface`, so they become ineligible in cave interior.

### Weather

`gameLoop climate/lightning → WeatherAudio.update → lazy loops / thunder one-shot`

Rain/storm loops are single retained handles. Cave state mutes outdoor loops. Thunder event IDs are de-duplicated per storm and one-shots use shared WorldAudio.

### Fire

`gameLoop current lit fires → createFireAudio.update → nearest-distance gain → one shared loop`

The implementation deliberately uses one burn loop and scans current fires to choose the strongest gain; it does not create a positional source per fire. Loop cleanup is explicit.

### NPC

Dialogue/barks use `npcVoicePlayback.ts → WorldAudio.playAt`. Player-reaction voice uses `playAtCancelable` and `NpcAgent` owns the returned stop handle. `createApp` clears `configureNpcVoiceSounds`, `configureNpcPlayerReactionAudio` and bark wiring during teardown.

Campfire delayed responses are owned by the NPC conversation lifecycle rather than browser timers; existing npc-045 logic guards interrupted conversation before the delayed cue.

### Fauna

Fauna/livestock vocalization routes through `animalSounds.ts → PlayAt`. Spontaneous calls share the existing small global concurrency window; there are no persistent audio nodes attached to an animal, so despawning an animal cannot leave a stale Object3D attachment. An already-started fire-and-forget clip can, however, outlive its actor because the shared one-shot API has no actor lifecycle ownership (see finding A2).

### Actions/combat

Action helpers reuse `PlayAt`; interruptible bow draw and NPC reaction use `PlayAtCancelable`. Ordinary hits/deaths/interactions are fire-and-forget one-shots.

### Rebuild/teardown

A `WorldBundle` rebuild does not recreate `WorldAudio`, `AmbientAudio`, `WeatherAudio` or `FireAudio`; they continue against the stable outer bundle/current inputs. This avoids duplicate listeners and duplicate ambient loops after rebuild.

Full app teardown disposes ambient/fire/weather loops and clears configured global callbacks, then calls `WorldAudio.dispose()`.

## 4. Findings

### A1 — Medium — world one-shots do not honor surface/cave spatial identity

**Affected flow:** world/NPC/fauna/action source → `WorldAudio.playAt()` → distance gain → playback.

**Files / symbols:**

- `src/audio/createWorldAudio.ts` — `WorldSoundPosition`, `playAtCancelable()`, `playAt()`
- `src/app/gameLoop.ts` — authoritative player cave-interior query already available
- `src/world/worldSpatialContext.ts` / current world-027 spatial-context mechanism
- representative consumers: `src/audio/npcVoicePlayback.ts`, `src/audio/animalSounds.ts`, `src/audio/actionSounds.ts`, `src/app/actions/groundActions.ts`

**Evidence:**

`playAtCancelable()` only computes Euclidean distance. If `position.y` is absent it substitutes `listenerPos.y`; it never checks whether listener and source belong to the same surface/cave context. Even when Y exists, rock/roof separation is only treated as ordinary meters. The audio path does not consume the shared `WorldSpatialContext` introduced for cross-space target isolation.

Some world action call-sites pass only `{ x, z }`, guaranteeing XZ-only attenuation for those events.

**Why wrong / fragile:**

A source directly above/below the player can be accepted acoustically across a cave boundary even though interaction/perception now has an explicit world-space identity seam. This creates a concrete cross-space presentation leak and keeps audio on a parallel, weaker interpretation of “nearby”.

This finding does **not** require HRTF or `THREE.PositionalAudio`; it is about source/listener world-space validity before playback.

**Affected consumers:** NPC speech/barks, fauna vocalization, combat/action sounds and other world one-shots near cave/surface overlap.

**Owner domain:** `world`.

**Existing plan coverage:** none. `world-027-player-spatial-context-and-cross-space-target-isolation.md` explicitly noted positional audio for separate follow-up and is already completed; reopening it would mix scopes.

**Recommended action:** new focused `world-037-audio-spatial-context-isolation.md`. Reuse canonical spatial context and preserve the existing audio bus/distance API.

### A2 — Medium — app teardown does not own pending or playing one-shots

**Affected flow:** `playOnce/playAt → playOnceCancelable → loadBuffer(url).then(...) → sound.play()` versus `WorldAudio.dispose()`.

**Files / symbols:**

- `src/audio/createWorldAudio.ts` — `playOnceCancelable()`, `playOnce()`, `playAtCancelable()`, `dispose()`
- `src/app/createApp.ts` — full app teardown

**Evidence:**

`WorldAudio` tracks loops in `activeLoops`, but has no equivalent registry/epoch for one-shots.

A pending `playOnceCancelable()` owns a local `stopped = false`. Only its returned handle flips that flag. Fire-and-forget `playOnce()` discards the handle, and `WorldAudio.dispose()` never reaches it.

Therefore:

1. start a one-shot whose buffer is still loading/decoding;
2. dispose the app/WorldAudio;
3. the promise may resolve afterward;
4. callback still calls `setBuffer()`, `sound.play()` and installs `onEnded`.

The buses have already been disconnected, so this is normally inaudible, but a WebAudio source is still created after owner teardown and lives until the clip ends. Already-playing fire-and-forget one-shots are likewise not explicitly stopped by `WorldAudio.dispose()`.

**Why wrong / fragile:**

Owner disposal is not terminal for all resources/callbacks it created. Repeated app create/dispose or teardown during decode can leave bounded but real post-dispose WebAudio work/resources, and future bus/listener refactors could turn this from silent leakage into stale playback.

**Affected consumers:** all UI/world fire-and-forget one-shots, including NPC ordinary voice/barks, fauna and action/combat sounds.

**Owner domain:** `world` (shared WorldAudio infrastructure).

**Existing plan coverage:** none. `world-033` owns destructive `WorldBundle` rebuild transaction safety; `WorldAudio` intentionally lives outside that boundary and this defect is full app/audio-owner teardown.

**Recommended action:** cover in new `world-038-world-audio-async-lifecycle-and-cache-recovery.md` by giving one-shots bounded owner tracking or an audio generation/disposed guard and stopping/disconnecting active sounds on dispose.

### A3 — Low — one failed load/decode poisons the URL cache for the rest of the session

**Affected flow:** `loadBuffer(url) → bufferCache`.

**Files / symbols:**

- `src/audio/createWorldAudio.ts` — module-level `bufferCache`, `loadBuffer()`

**Evidence:**

The cache stores `Promise<AudioBuffer>` before resolution and never removes it. If `AudioLoader.loadAsync(url)` rejects because of a transient fetch/decode failure, that rejected promise remains under the URL. Every later playback retrieves the same already-rejected promise and cannot retry until the JS module/session is recreated.

**Why wrong / fragile:**

Caching in-flight/successful work is correct; caching failure forever changes a transient loading failure into a session-long loss of that sound.

**Affected consumers:** every loop/one-shot sharing the failed URL. For an ambient loop, the owning handle also remains allocated at zero gain and does not get another load attempt.

**Owner domain:** `world`.

**Existing plan coverage:** none.

**Recommended action:** cover in `world-038`; evict only the same failed promise on rejection so a later request can retry, without allowing duplicate concurrent decodes.

## 5. Architecture observations

1. **The previous LoadingManager fact is still true.** With Three r185, `new AudioLoader()` uses `DefaultLoadingManager`, and decode creates `<url>#decode`. Seedvale currently does not subscribe to that manager, so no loading-screen/progress defect was found.
2. **No `PositionalAudio` exists in current runtime.** This is documented and not itself a finding. `playAt` is start-time distance attenuation using ordinary `THREE.Audio`.
3. **Start-time spatial snapshot:** gain is not recomputed after a one-shot starts. Long voice/howl clips can therefore become spatially stale if source/listener moves. Current code/doc contract explicitly describes distance gain at play start, so this review records it as an architecture limitation rather than a confirmed defect.
4. **Loop ownership is coherent.** Ambient/weather/fire have one retained handle per layer and explicit dispose; no duplicate loop-on-rebuild path was found.
5. **Autoplay handling is bounded.** `pointerdown`/keydown resume listeners are added once per WorldAudio instance and removed on dispose; no current defect found.
6. **Ambient cave transition is coherent.** Surface beds and the owl event are suppressed through `mix.surface`; cave loop is lazy and retained.
7. **Per-frame work:** `WorldAudio.update()` scales with active ambient loops only. `FireAudio.update()` performs one nearest-fire scan per frame. No evidence in current code/reviews justified a separate performance finding for these bounded paths.
8. **Fauna spontaneous limiter:** the module-level six-second recent-play array survives world rebuilds, but is bounded to at most three timestamps and only causes a short presentation throttle; recorded as minor lifetime coupling, not a finding.
