## 1. How to read this matrix

`prop` is display input unless explicitly a callback/host; `event` is output, not necessarily a gameplay command; `model` includes both its prop and `update:*` event. A model carrying an entire Inventory/Account is not a validated V1 command. Types are transcribed from the actual Vue macros, including optionality; imported types stay named, with their defining dependencies listed in §4. Rows marked `$imported` delegate a third-party interface rather than declaring individual gameplay values.

AVAILABLE = same data/function exists; RENAME = equivalent data under a compatible different label/shape; DERIVED = presentation-only computation over real V1 state; MISSING-TEMP = selected/planned mechanism not available yet; MISSING-UNKNOWN = no confirmed implementation/decision; NOT-PLANNED = outside agreed direction; INCOMPATIBLE = superficially similar but different semantics/authority. Outer structured props may be INCOMPATIBLE while many constituent values already exist: §2 decomposes them. No type assertions, zero-filled donor records or mock values may bridge those cases.

**Author-approved D4:** unavailable controls stay rendered with native `disabled` and exactly `opacity-5`, preserving layout. Keep an adjacent readable reason outside the dimmed control and block dispatch, including stale/programmatic commands. Missing display data uses an explicitly unavailable, fixed-space `placeholder`; never zero-fill a metric or color unknown body regions healthy. Do not use `hidden`/`omit` to resolve missing functionality. Screen selection/composition remains separate: D4 does not select every donor demo/debug screen or undo D0 dialogue exclusion. A structural mismatch with real V1 data calls for adapting its presentation contract, not disabling existing working V1 functionality. D1 selects item details first; D3 selects current V1 equipment effects. These are planning choices, not execution approval.

### Shared native primitive family outside game/ui

The donor world screens also use `src/components/ui/button/Button.vue` (not the item Reka wrapper). Its exact declared inputs are `variant?: ButtonVariants['variant']`, `size?: ButtonVariants['size']`, `class?: HTMLAttributes['class']`, `type?: 'button' | 'submit'` (default button); no defineEmits. Native attributes/listeners fall through to the button. V1 UiButton already owns variant `primary|ghost|danger`, class, disabled and type with min-h-11. Map variants/styles (RENAME), preserve native disabled/type/click (AVAILABLE), and retain V1 target size. Shared Label/Slider/Switch/Badge visuals in settings do not authorize adopting useSettings or its save schema. Prefer existing V1 primitives; any new widget requires the same real-value and event mapping at its screen boundary.

### Non-prop owners and implicit commands

- `SceneView` provides modalStackKey, hotkeyTableKey, toastQueueKey, uiEventsKey and playerDownKey from donor session infrastructure. Do not provide fake versions just to mount a screen in V1.
- `WorldInventoryScreen` calls its `read`, craft/eat/water host getters and host commands, caches hosts and polls every 500 ms while open. V1 already publishes reactive snapshots and owns world teardown: discard donor polling/cached host wiring.
- Rich `InventoryScreen` calls donor equip/unequip/removeInstance/repair/sharpen functions and publishes whole Inventory updates. Its comment says smith work is free for judging numbers. It is a sandbox even if it renders convincingly.
- `MerchantScreen` calls quoteBasket/settleBasket/buyService and replaces player/merchant model values. `TradePanel` forwards next Accounts; this cannot become a V1 transaction authority.
- `CraftPanel` calls host.learned/context()/busy()/start(); `CampfireSection` fires() is a read; fuel(id)/putOut(id) are commands, not display callbacks. Existing V1 fire, fuel and cooking must be traced independently rather than introducing donor hosts.
- `AmmoPanel` changes a local weapon/ammo preference only. A working selector/demo does not demonstrate V1 ranged execution or persistence.
- `ConversationPanel` auto-emits ack after rendering an NPC line, registers a non-pausing modal and global digits. D0 excludes its UI; no auto-ack/option truncation/hotkeys are imported.
- `MapScreen` directly calls annotation/edit/publish-related methods on its WorldMap, uses session/world scope guards and a separate editor modal layer. V1 NotesScreen is not that owner. Keep only existing V1 capabilities unless D7 approves new ones.
- `SettingsPanel` writes useSettings, subscribes weatherOverride and exposes devtools. `GameMenus`/AppShell bind donor save/session roots. These are not prop-free reusable screens.
- `HelpScreen` binds donor help table; MessageHistory requires toastQueueKey and donor L log binding. Preserve V1 L quests. SceneOverlay/NPC debug counters are not a reason to expose donor dev menus.
