## 0. Session protocol (read once per session)

1. `git pull --rebase origin main`. Read this file, then the Strategic Brief §1 (decision table + D4 policy). Do not load the whole dossier.
2. **Pick a task:** first resume any `in progress` task carrying a `Resume:` note; otherwise take the **first `ready` task** whose model column fits you (a `blocked (Qn)` task becomes `ready` when Qn is `done`). Mark it `in progress (<model>, <date>)`, commit + push that one-line change before long work, so parallel sessions do not collide. An `in progress` task without a `Resume:` note and with no related commit for >24 h is stale — take it over and say so in the status.
3. Follow [CLAUDE.md](../../../CLAUDE.md) task routing for the task itself (CODE_INDEX → STATE → plan → source). For a formal plan, use `pnpm claude:preflight <plan>`.
4. Finish = implement → targeted verification → update owner docs (plan/notes/tracker/STATE) → commit → push. Then set the task `done` here with a one-line result + commit link, unblock dependent tasks, and continue with the next `ready` task.
5. **Leaving a task unfinished** (context or session ending): commit work-in-progress that keeps `main` building, and append to its status cell `Resume: <next concrete step; files; open question>` so a bare "Continue" can pick it up.
6. **Nothing `ready`:** do not invent scope. Report to the author the blocked tasks and the §3 questions, with short options to unblock them.
7. **Stop and ask the author** (Polish, survey-style options) instead of guessing when a task hits a `Stop if` condition, an open decision (D2, D5–D8, D10, D12–D14 or an area question), a visual compromise, reduced density/simulation, or omission of an agreed feature. Record the question in §3 and move to the next task that is not blocked.

### Autonomy granted (author, 2026-10-29)

- Autonomous sessions may make **documentation and full runtime implementation changes directly on `main`** (commit + push per CLAUDE.md), including P1 performance slices.
- This does **not** approve open decisions or widen Revival scope. D4 Performance-First still governs *what* runtime work may merge: P1 A/B/C/D slices, recorded D4 exceptions (map raster `ui-input-046`, dialogue reskin) and critical fixes only. Other runtime work stays deferred until P1 exit.
- Agents cannot produce certified performance evidence: native **Windows Intel Arc** runs are executed by the author. WSL2 runs count against the parallel WSL baseline and can green-light a slice (see below); headless runs are diagnostic only. For a keep/revert question, land the change behind a clearly reversible boundary (single commit, or a toggle where the code already has one), write the A/B instructions in the plan/notes ([Arc runbook](../../performance/2026-10-27--arc-baseline-runbook.md)), and list it in §4. Never claim FPS gains without matched evidence, and always name the platform.
- **Parallel WSL2 baseline (author, 2026-10-29):** benchmarks may also run on WSL2 against their own WSL baseline (same SHA/fixture/config recorded). Chrome on Windows uses ANGLE **D3D11**, WSL2 Chrome uses **OpenGL** (Mesa, D3D12 translation): CPU submission, driver and GPU-timer behaviour differ, so never compare or mix WSL numbers with Windows numbers, and label every result with its platform. A good WSL A/B (beyond same-session WSL noise, no p95/p99 or hitch regression) is a **green light**: land/enable the optimization, then list it in §4 for native Windows confirmation; revert if Windows shows a regression or the change fails visual checks.
- **WSL green light for CPU-side slices (author, 2026-10-29, Q14):** WSL is often GPU-bound, so mean FPS cannot rise there. A CPU-side slice is green-lit when the WSL A/B shows **no regression** (mean FPS, p95/p99, hitches) **and** a gain estimated from structural evidence (counters, census, RENDER/frame p50, trace self-time). If neither the estimate nor the WSL numbers are convincing, the Windows A/B decides before enabling.
- Keep each slice an independently revertable commit; never combine two keep/revert candidates in one A/B (see brief "Deferred performance experiments").
