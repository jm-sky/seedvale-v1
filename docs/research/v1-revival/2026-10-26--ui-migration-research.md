## 3. Minimal integration architecture

Retain `createApp → existing V1 facades/mount/store → current screens → presentation leaves`. Add small, screen-local read-model transformations only where a donor leaf needs another layout. Do not create a central donor compatibility store, second inventory, event bus or parallel action registry. Prefer changing donor leaf inputs to V1-shaped view props over filling a donor Inventory/CharacterState with invented fields. Keep types near the consuming screen and reuse existing `InventoryGroupView`, `CharacterPresentation` and merchant contracts.

The inventory snapshot is produced by `refreshInventoryScreen` in `src/app/createApp.ts:3204` from authoritative Inventory/HeldTool/equipment/primaries, not reconstructed by Vue. Its callbacks at `:3162` route to `src/app/inventoryWiring.ts`, survival and placement. Keep this boundary and refresh timing. V1 inventory currently gates simulation; donor world inventory/modal defaults must not change it. UI-local selected IDs, tabs, sorting and drafts are acceptable, cleared/revalidated on close and world replacement.

Visual tokens: copy selected warm neutral/primary/status palette values and spacing/typography rules from donor `src/css/style.css`; map V1 `panel`, `panel-backdrop`, `ink`, border/ring aliases deliberately. Do not copy the demo body's sky/ground background, global `*`/html rules or replace every neutral utility globally in stage 1. A scoped panel theme makes screenshots and rollback tractable. Both use Tailwind 4/Vue 3.5, but donor TS6/Vite8/Three/reka upgrades are not prerequisites. Alias `@` resolves differently: V1 UI aliases cannot silently point to donor `@/game/data`.

### Standalone demonstration screens — author scope addition

**Author decision D9 (2026-10-26):** include demonstration screens alongside the migrated in-game UI. They must render the **same adapted presentation components**, rather than a separately styled copy. Begin with item details in Stage A; expand demonstrations with each later selected screen. The author has not selected an exhaustive list of donor sandbox pages.

Use a separate, clearly labeled demo entry that can run without starting a world. Fixture inputs use the adapted V1 view contracts and explicitly labeled sample data. Demo-local selection, fixture editing, reset and simulated callbacks may exercise presentation independently; label simulated effects clearly. They must never mutate an active game's Inventory, save slots or WorldBundle, nor import donor gameplay stores merely to make a screen work. Unavailable mechanics still receive unavailable values and disabled + opacity-5 controls; do not invent gameplay capabilities. Fixture data is allowed in this isolated demo, never as a production fallback.

The demo is useful for visual review and component interaction checks. It does not establish in-world command correctness, persistence or completed mechanics. Donor Player–NPC dialogue UI/UX remains excluded by D0. Carry D9 into the next Cursor proposal as a required deliverable, while implementation remains unapproved.

## 4. Preservation contract and risks

| Existing V1 behavior that must survive | Integration hazard / required check |
| --- | --- |
| Count stacks, exact identity gear, qualities, food batches/species/freshness, liquids; mass and size limits | Donor array-of-instances is not V1 inventory. Keep group and instance references separate. Distinguish real zero from unavailable. Liquid fill is not durability; legacy sort-only 100 is not pristine condition. |
| Physical drop/pickup with identity and provenance | V1 `dropItems(kind,amount)` chooses first owned instances; donor remove-by-selected-ID does not match. Keep current kind/quantity drop semantics; exact-selected-instance drop would be a separate product/backend change. |
| HeldTool, primary melee/ranged assignments, drawn combat mode, valid armor slots | A single donor weapon field loses ownership and controls. Resolve real IDs; no duplicate refs, no stale item command. Preserve tool/torch synchronization. |
| Armor protection and all restrictions: attack stamina, recovery, movement, sprint | Use shared V1 equipment resolver for live and hypothetical loadout. Do not present donor weighted cut/pierce/blunt, DPS, price or armor durability as equivalent. Future layers/areas require the separate mechanical contract first. |
| Trade with any living NPC including empty stock; finite merchant goods; barter/social pricing, exact quality and coins; horse offers | Keep `onSettleTransaction` and owner-aware live revalidation. Donor next Account objects never authorize V1 mutation; UI prices are previews. Preserve reserved artisan outputs and insufficient-coin refusal. |
| Artisan deposits, real profession production, exact once pickup; acquisition/loot/gifts | CraftPanel and free sandbox repair cannot replace artisans. Never make a displayed service operational without a real V1 command/cost/path. |
| Fixed base/effective SPEA, earned XP, eight skills, active conditions, settlement selection, reputation/renown/badges | Do not relabel donor progression/attributes as V1. Keep stealth toggle and targeted Medicine/Repair/Traps entry points; read-only donor skill details are insufficient. |
| Quest report vs offer vs required action; ordinary/help groups, gift/wage/join/food/water/area knowledge | V3 dialogue UI excluded. Closing/reopening resets category. Pointer-lock restoration on Q must remain within the key gesture. |
| E press/release, R/V, cycle target, aiming/throwing, mouse/touch; nested Escape, focus and cancellation | Preserve V1 overlay stack, typing guards and gameLoop gates. Never register donor and V1 modal/hotkey stacks for one screen. Dialog close cancels UI only according to existing semantics. |
| Save/load/new game/rebuild lifecycle | `invalidateWorldBoundUiSessions` clears handlers/sessions. In-flight promises and stale refs must not affect replacement WorldBundle. No save schema change for presentation-only work. Reopen screens from freshly produced state after load. |
| Maps: learned/estimated locations, km scale, navigation slots, minimap pointers | Donor raster, legend and world units cannot replace V1 discovery. New personal annotations require a separate approved persistent feature, not localStorage hidden in a component. |

## 6. Verification and closure

Source review establishes contracts and ownership. Automated checks must prove type safety, units, command routing and non-mutation of read-only projections. Browser checks must prove focus/Escape, pointer lock, mouse/keyboard/touch operation, responsive layout, reopening and real state changes. Author screenshots establish visual acceptance only. The draft stages specify focused checks; no broad simulation benchmark is justified for this documentation work.

Before any implementation handoff: capture the author's D1–D8 answers applicable to that stage, preserve unresolved alternatives, refresh affected source pins and create the repository-standard active plan only after approval. This research does not approve a screen replacement, gameplay change or rollout.
